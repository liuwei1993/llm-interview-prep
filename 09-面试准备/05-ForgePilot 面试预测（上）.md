#### 7.3.3 面试真题预测

在面试前，其实我们就可以根据我们的简历，预测很多的面试问题了。因为很多面试就是围绕你简历去问的。

我分为几类问题，大家也可以按这个思路来自己预测： 

1. **必考问题**：你的项目是什么，简单介绍一下。（能想到必考的只有这一个）

2. **高频问题**: 任何你写在简历上的每一句话相关的内容，你说出去的（比如在介绍项目时）提到的每一个技术栈，都可是高频考题。

包括一些通用问题：你的项目中遇到了什么最难的问题，如何解决，也属于高频。

3. **重点内容**：比如Agent项目的，记忆怎么设置，上下文如何压缩，等等，这些属于重点内容。

##### 7.3.3.1 ForgePilot

###### 7.3.3.1.1 必考问题

**7.3.3.1.1.1 ****简单介绍你的 forgecopilot 项目**

**💡 答题思路：**

从**痛点-功能-架构-结果**四个方面概述。

**🗣️ 参考回答：**

ForgePilot 是我设计的一个**面向企业研发场景的 AI 研发平台**，不是重新做一个编码助手，而是复用成熟 Agent 的能力，补齐企业上下文和交付流程，让 AI 从“能改代码”走向“能交付可审核的修复”。

**这个项目主要解决四个痛点**：**第一，上下文分散**，企业代码跨仓库、跨分支，Bug 信息也散落在工单描述、评论和附件中，通用 Agent 很难拿到完整信息；**第二，工程流程复杂**，公司有特定的构建和测试方法，Agent 经常需要工程师带着走；**第三，人工评审跟不上**，AI 生成代码很快，但人理解和审核修改仍然耗时；**第四，远端模型的调用成本和数据外发风险**，因此我们规划接入公司自研本地模型，优先承担工单理解、信息提取和任务分类，减少这部分任务对远端模型的依赖，复杂的代码分析再交给主模型，并对外发数据进行管控。

**围绕这些问题**，平台设计了**代码问答、Bug 修复和辅助评审**三个核心功能。代码问答帮助开发者理解项目、定位逻辑；Bug 修复从 TAPD 工单出发，串起任务整理、代码定位、修改和测试，经人工审核后受控创建 PR；辅助评审则把变更意图、关键 diff、影响范围和验证证据组织起来，帮助人更快理解和验收修改。

**架构上，**前端采用 React 和 TypeScript，后端使用 Node.js，核心分成**任务编排和插件化执行两层**。上层由本地模型整理需求，Harness，也就是流程控制代码，负责校验、权限、路由和任务状态管理；下层通过 Cordis 装配模型、检索和执行工具，默认由 Pi 驱动 Agent 循环，完成定位、修改和验证。同时，会话记录保存执行过程，经过验证的项目经验沉淀为长期记忆，供后续任务复用。

**整个设计的核心是**：**确定的流程交给程序，需要探索的步骤交给 Agent**，在保留 AI 灵活性的同时，让企业研发交付更可控、可追踪。成果方面，前期平台已经被多个团队使用，在真实 Bug 任务集的对照评测中，端到端交付成功率相比ClaudeCode提升了 **32%**，也为 ForgePilot 的进一步设计提供了实践依据。

###### 7.3.3.1.2 高频问题

**7.3.3.1.2.1 ****我看你简历写了“SWE-bench 修复 Agent 评估”，这个是如何做的，可以自己讲一讲吗？**

**💡 答题思路：**既是简历上写了，面试官可能问的内容，也其实是面试官直接问你：你的项目是如何做Agent评估的问题回答。思路是参考[笔记Agent评估方法](https://my.feishu.cn/docx/GikId1snboM6LyxxGPXc0kDdnub#doxcnPYa7KqkNKJRmGjzsRmuJhe)，进行设计。

**🗣️ 参考回答：**

评测思路是借鉴 SWE-bench，用企业内部历史 Bug 出题，让 Agent 修复，再用测试验收。具体分三步。

**第一，准备数据集。** 从历史 Bug 中选取工单理解、跨模块定位、构建测试等典型任务。每条整理成“工单描述和日志＋修复前代码版本＋环境配置＋验收测试”。验收测试包括能复现原缺陷的测试和相关回归测试，历史修复答案不提供给 Agent。数据分成调试集和最终测试集。

**第二，批量跑对照。** 让通用 Agent 基线和定制平台跑同一批任务，固定模型版本、代码起点、环境和预算，使用相同验收标准。每条任务保存补丁、测试结果、工具调用记录、耗时和费用。

**第三，汇总结果，从三个方面比较。**

- **结果上**：检查补丁能否应用、构建是否通过、缺陷验证和相关回归测试是否通过。按统一成功条件给每条任务记通过或不通过，汇总成**任务解决率**，再按任务类型看哪类表现更好。
- **过程上**：对照工单和执行记录，将信息遗漏、代码版本定位错误、重复无效搜索、未验证就宣布完成等问题分类，统计各类问题的出现比例，了解任务主要卡在哪里。
- **成本上**：汇总平均单任务耗时、模型费用、工具调用次数和人工接管比例，比较两套方案的投入。
最终看的是一份对照汇总：**解决了多少任务、主要出错在哪、平均花多少资源。** 任务解决率单独计算，过程和成本不加权到这个指标里；32% 比较的就是两组任务解决率的相对变化。

7.3.3.1.2.1.1 **追问：你提到在 180 条任务上，成功率从 31.11% 提升到 73.33%，相对提升约 135.71%，是怎么测出来的？什么算成功？**

> 你看到讲解视频的时候，这个问题和参考答案可能改了，不过思路是一样的，以笔记为准哈，你看到的笔记永远是最新的。
>

**💡 答题思路：**面试官有非常大的可能性会追问我们简历上的数字的细节，数据是怎么统计的，计算方法是什么，相对提升还是绝对提升？这是我们面试前需要自己弄清楚的。 我们这个问题的回答的关键，是想清楚这个成功率怎么判断：按照什么标准来统计任务是否成功？ 这个是下面的答案的第一小段讲的。 

讲清楚如何判定成功，后面就是解释数据了，我们测了多少数据集，测试的Baseline是什么？

**🗣️ 参考回答：**

我们主要从两个维度判断任务是否修复成功：**一是能不能自主完成，二是修复结果是否符合验收要求。**

首先是自主完成。从代码定位、修改，到编译构建、运行测试，以及失败后的返修，都需要 Agent 在规定预算内自行完成。过程中不能由人工帮它改代码，也不能人工告诉它根因和具体修法，但允许它根据构建、测试的反馈自行调整和重试。任务结束后人工审核结果，不算帮助它完成修复。

其次是代码正确性。我们参考了 SWE-bench 的做法，为每条任务准备对应的单元测试、必要的端到端测试和相关回归测试。核心是验证两件事：**原来能够复现 Bug 的测试，修复后要通过；原本正常的功能，修复后不能被破坏。** 这里不是模型说自己修好了就算成功，而是必须实际运行测试，由评测程序检查执行结果。

除了功能测试，**每条任务还会整理相关的架构约束和关键设计要求**，比如不能破坏公共接口兼容性、不能绕过权限校验、不能违反模块依赖关系。能够自动检查的通过规则和测试验证，其余通过代码审核判断。即使测试通过了，只要明确违反这些硬性约束，我们也不认为修复成功。我们不要求它的代码和历史修复 PR 一模一样，但要求它修得对，而且符合项目的工程要求。

只有自主完成和结果验收这两个维度都通过，我们才把这条任务记为端到端修复成功。

比较时，让 Claude Code 和我们的框架在同一批任务上，使用相同模型、代码起点、预算和验收标准分别运行。在包含 180 条 Bug 任务的评测集中，Claude Code 按照上述标准通过了 56 条，成功率约为 **31.11%**，主要问题集中在检索不到所需代码或上下文、生成的代码违反架构约束，以及修复结果无法通过测试这三个方面。使用我们的平台后，同一批 180 条任务中通过了 132 条，成功率约为 **73.33%**，比基线多通过了 76 条。因此，成功率**相对提升约 135.71%**，计算方式是（132 − 56）÷ 56；成功率**绝对提高约 42.22 个百分点**，计算方式是（132 − 56）÷ 180 × 100 个百分点。

7.3.3.1.2.1.2 **追问：这个项目有几个研发？你具体负责什么？哪些能力是你做的，哪些来自开源？**

**💡 答题思路： **很合理的追问，一开始我给这个项目的定位就是企业级的项目。功能也比较复杂，既有本地模型嵌入，又有测评，又有鉴权，又有不同的UI模式，插件化设计，以及要上线的。**这些不可能一个人完成！**

所以你必须明确你负责那一块，这样其实也是为我们减轻压力，如果有哪个地方实在答不上来，可以找理由说自己没负责这一块！

说自己负责哪一块：就根据你哪一块熟练，哪一块有价值（比如jd需要，或者面试官关注来定）。这个应该和你写在简历的内容相对应。结合我自己的例子来说，我会说我负责**本地模型适配+Agent核心编排**（记忆，压缩，评测）这两块。**前者是我们做过的项目，要体现我们的后训练，部署能力。 后者是Agent最核心的能力，我们也比较熟练。**

**🗣️ 参考回答：**

这个项目是团队协作的企业级研发平台，研发团队一共 6**人**，不是我一个人从前端到模型全部做完的。平台涉及工作台、企业系统接入、代码检索、Agent 执行和评审等多个模块。我主要负责的是两块：**Agent 核心 Harness 的设计，以及本地模型的适配工作**，也是我简历重点写的部分。

第一块是 **Harness**，也就是围绕 Agent 执行内核的流程控制和上下文管理。我重点关注三个方面：**记忆、压缩和编排**。记忆方面，区分当前任务的状态与执行上下文，以及后续任务可以复用的、经过验证的项目经验；压缩方面，处理长任务中对话和工具结果不断累积的问题，重点考虑怎样保留任务目标、关键证据和未完成事项，而不是简单截断历史；编排方面，把工单整理、信息校验、Agent 执行、验证反馈和人工审核串起来，明确哪些步骤由程序控制、哪些交给 Agent 探索，以及失败或预算耗尽时如何停止、转交处理。这里不是重新实现一套 Pi，而是设计企业任务如何在已有执行内核上受控运行。

第二块是 **本地模型适配**。这部分在当前方案中仍是规划方向，主要由我负责适配方案：优先让本地模型承担工单理解、信息提取和任务分类，并设计它与 Harness 之间的输入输出约定、结构化结果校验和异常回退机制。复杂代码分析再交给主模型。我的职责重点是让模型适合这条业务链路，而不是把公司基础模型的训练也算成自己的工作；是否进入微调，要根据任务评测结果再决定。

开源复用方面，**Pi 提供 Agent 循环，Cordis 提供插件注册、依赖注入和生命周期管理**；我的工作重点是这些组件之上的企业任务控制、上下文策略和模型适配。工作台、企业检索底层、统一认证和部署等不作为我的主要负责范围，具体由谁负责按团队实际分工说明。我需要了解它们和 Agent 的协作接口，但不会把其他模块的实现都算在自己身上。

所以，概括来说，**团队交付的是企业级研发平台，我主要负责的是让 Agent 带着合适的上下文、按受控流程执行任务，以及本地模型在这条链路中的适配。**

7.3.3.1.2.1.3 追问：你提到了现在180个数据集上仍然有快50个数据集没通过，你觉得下一步应该如何提升？

**💡 答题思路：**这一个题考察对于项目评测结构的展望，如何进一步提升，下一步是什么？也是我们应该提前准备到的。 （[202508 阿里淘天秋招一面](https://my.feishu.cn/docx/GikId1snboM6LyxxGPXc0kDdnub#doxcnShwGx1ov6U5gsMngYh9LBh)面试官就问候选同学，你简历写的这个指标，该如何进一步提升？）

通过这个题，可以锻炼我们思维发散的能力，针对具体问题，如何解决，也是很多时候面试官喜欢和你去讨论问题的。我们可以通过这样一些问题，锻炼我们对于这些问题的变通，扩展的能力。 

**🗣️ 参考回答：**

目前我们的系统下，系统出现的错误主要在两个方向： 

**1.跨模块修复能力不足：**Agent很容易把当前bug修复好了，但是破坏了其他功能，在评估时卡在因为导致其他功能发生回退，导致错误。我认为这里的优化方式是，修改检索模块和Harness，不光检索相关要修改的代码，也检索他的代码调用层级关系，同时加强对于架构约束模块。让Agent在看清楚全局调用链和架构约束的视角下， 针对性修改问题。

**2.Agent很容易陷入死循环，在错误方向上不断深入钻牛角尖：**很多时候，Agent一开始分析出来的修复方向就不对，在错误的方向上，在ReAct框架上反复重试，浪费时间且无法最终修复。 对此，我考虑在 Harness 中增加无进展检测，当同类错误反复出现时，触发独立的反思 Agent，根据修改记录和测试反馈重新检查修复方向，再让 Pi补充调查或换一个方案，而不是机械重试。

7.3.3.1.2.1.4 追问： 引入这套评估体系前后，整个产品链路最明显的变化是什么？

**💡 答题思路：**

灵感来源于[202508 阿里淘天](https://my.feishu.cn/docx/GikId1snboM6LyxxGPXc0kDdnub#doxcnjQj8xmYFVcG7ZD22ETXFge)的面试官 的提问。

这样的问题不是特别好提前预测准备好，不过如果我们知识比较扎实，现场懂得变通，这个题目也不会说答不出来，这个问题我们回答的出发点就可以从测试驱动开发来说。引入了评估系统后，每个环节哪里出现了问题，我们都能够实时辨别，针对性修改，同时修改了新内容也可以及时监控是否会引发回归。测试驱动开发的思想，我们在[Agent评估章节](https://my.feishu.cn/docx/GikId1snboM6LyxxGPXc0kDdnub#doxcnPYa7KqkNKJRmGjzsRmuJhe)就讲过，理解了这一小节的思路，这个题也可以回答了。

**🗣️ 参考回答：**

我觉得最明显的变化，是整个产品从主要依赖个别案例和人工反馈调试，转向了**有明确验收标准的、评估驱动的迭代方式**。这个思路借鉴了测试驱动开发：先明确什么算完成，再根据失败样本针对性修改，最后通过回归验证改动是否有效。

ForgePilot 的链路比较长，包括工单理解、上下文准备、代码检索、Agent 修改，以及后面的构建测试。最终修复失败，不一定是模型不会写代码，也可能是前面漏了信息、拿错了上下文，或者执行过程中丢失了约束。所以评估不仅要告诉我们成功了多少条，还要结合各阶段的输入输出和执行记录，帮助我们定位失败发生在哪里。

（比如生成的代码违反了“不能修改公共接口”这个要求，我们就需要检查：是本地模型解析工单时没有提取出来，还是 Harness 没有把约束传递给 Pi 执行层，或者长任务压缩时把这条约束丢了。如果约束一直都在，那才进一步看模型执行和验收机制。每个环节都有明确记录和追踪，帮助我们把同一个失败结果可以对应到不同的改进动作，测试驱动开发。)

另外一个变化是，**每次修改都需要验证有没有引入回归**。我们的执行能力通过 Cordis 插件化装配，检索策略、模型和上下文策略都可以调整。但换了检索器，不能只看搜到了更多代码；改了压缩策略，也不能只看 Token 降低了。还需要跑相关回归任务，检查最终修复成功率、架构约束遵守情况，以及耗时和成本有没有退化。

**落到交付环节，完成的标准也会更加明确**：不是生成补丁或者模型宣布完成就结束，而是需要有构建、测试和约束验收的证据。能够自动判定的失败，可以反馈给 Agent 在预算内返修；不能自动处理的，再交给人工审核或接管。

⚠：我还能想到一些面试官会追问的内容：比如为什么使用Pi-Agent？ 怎么用的Pi-Agent？插件化如何实现的？这些来不及准备了，自己可以多想一想。

**7.3.3.1.2.2 已经有 Claude Code 等通用 Coding 平台，为什么你们公司还需要搭建自己的平台？**

**💡 答题思路：**这个问题，我觉得是大部分面试官看到我们项目，第一个自然的反应。不过我在立项的时候，就想清楚了这个事情的答案，找了做这个事情的真实的痛点。

**🗣️ 参考回答**

我们不是要重新做一个 Claude Code，而是**复用通用 Agent 的编码能力，补齐企业场景中的上下文、交付流程和安全要求**。主要有六个原因。

**第一，大规模代码检索。** 团队代码资产超过 300GB，涉及多个仓库和分支，仅靠当前本地工作区搜索可能漏掉相关代码或找到错误版本，需要接入企业检索服务。

**第二，企业任务理解。** TAPD 缺陷单的信息散在描述、评论、附件和关联单中，需要先整理成完整任务，避免 Agent 根据不完整的信息走错方向。

**第三，减少流程试错。** 公司有特定的构建、排障和测试方法，我们把确定的流程固化下来，不让 Agent 每次重新摸索，也减少工程师带路的时间。

**第四，提高交付成功率。** 写完代码不等于修复完成，我们关注构建、测试、失败反馈和返修的完整闭环。真实任务数据集上的评测结果显示，定制平台相比通用 Claude Code 流程，端到端交付成功率提升了 32%，这也是定制工程流程价值的一个依据。

**第五，降低人工 Review 成本。** AI 写得快，人不一定审得过来。平台将变更意图、关键 diff、影响范围和验证证据组织起来，帮助 Reviewer 快速理解修改，聚焦风险判断。

**第六，逐步适配公司自研本地模型。** 这是规划方向：让适合的任务在公司受控环境内处理，减少敏感数据外发，再通过内部授权数据微调改善特定任务效果，并评估成本收益，而不是默认本地模型一定更便宜、更准确。

所以，单点需求可以用 MCP、Skills 解决；**平台化的意义，是让这些能力在团队内统一复用，形成从任务到可审核交付的完整流程，而不是重复造编码工具**

**7.3.3.1.2.2.1 追问：你讲到的降低人工 Review 成本，这个是怎么理解，可以展开说说吗？**

**💡 答题思路：**在你讲了某个功能，内容，没展开讲的时候，面试官很容易追问。这个降低Review成本，也是我在需求一开始的时候，就设计的一个功能。当我们想清楚了功能设计，这个题很好回答。这个也是一开始我说，即使时间有限，没时间设计具体文档，也先想清楚项目的痛点，功能，架构这些最基本的问题。

**🗣️ 参考回答：**

我理解的降低人工 Review 成本，主要是**降低人理解代码变更的成本，而不是让 AI 替人批准代码**。AI 加快了代码产出，但工程师仍然需要判断这些修改为什么做、是否合理、有没有验证。尤其当代码不是自己写的，一个 PR 又涉及多个文件时，理解修改思路本身就很耗时。

传统 PR 主要按文件展示红绿 diff，它能告诉你“哪些行变了”，但跨文件的修改关系往往需要 Reviewer 自己拼出来。我们希望参考 CodeRabbit Change Stack 按逻辑组织变更的方式，**把分散在多个文件里的 diff，按修改意图重新分组，并关联说明和验证证据**，而不只是额外生成一段 PR 摘要。

举个例子，Agent 要修复“请求失败后无限重试”的 Bug，可能同时修改配置文件、请求逻辑和测试文件。传统方式需要人来回翻这三个文件；我们希望先说明这次修复的目标，再按“定义并执行重试上限、传递重试次数、验证停止条件”组织阅读顺序。Reviewer 点开一个逻辑分组，就能看到相关的真实 diff，以及对应的测试和执行结果，再判断次数边界是否正确、测试是否覆盖原始问题。

这样降低的是**寻找相关代码、跨文件切换和重建修改思路的成本**，让人把精力更多放在行为是否正确、边界条件是否覆盖上。同时可以折叠格式调整、代码搬迁等噪声，但必须保留完整原始 diff 和未分组变更；说明要能跳转到代码和证据，未验证的地方明确标出，不能因为 AI 解释得顺就认为代码正确。

所以，这个功能的定位是**面向 AI 研发交付的变更理解与验收辅助**。目前属于设计方案，后续需要通过评审耗时和问题发现情况验证它是否真的降低成本，而不是只看页面是否更好看。

**7.3.3.1.2.3 ****你在简历里提到了上下文压缩和运行态恢复，具体是怎么做的？**

**对应简历以下描述，预测的问题：**

> 针对长任务上下文超限与摘要后状态丢失，按窗口预算压缩历史、保留近期交互，并保存与恢复关键运行态；通过工具输出分档裁剪、完整工具调用轮次回收及有界恢复与熔断，减少上下文溢出引发的重复失败。
>

**💡 答题思路：**

这道题的回答**严格围绕简历要点展开**，解释清楚简历写了啥。这个下面的策略，其实也是很多经典Harness框架，使用的一些常见方法了。

1. **按窗口预算压缩历史、保留近期交互**：用窗口占用比例解释触发条件——低于 80% 正常执行，达到 80% 先裁剪工具结果，仍达到阈值才摘要旧历史；按窗口容量约 16% 的 Token 额度保留近期交互，而不是固定保留几轮。
1. **工具输出分档裁剪、完整工具调用轮次回收**：说明**短、中、超长**结果分别如何处理，以及为什么调用消息和对应结果必须成组处理；用“之后只把摘要发给模型，完整消息保存在会话记录里”解释回收，避免抽象措辞。
1. **保存与恢复关键运行态**：讲清记录哪些任务信息，以及压缩后如何继续原来的工作；用“等待回归测试结果”的例子说明，避免只说保存状态、不说实际用途。
1. **有界恢复与熔断、减少重复失败**：明确溢出后先缩减输入，再重试原任务，最多一次；仍然超限就保存进度并停止自动执行。这里的熔断是任务级停止自动重试，不扩展为服务级熔断器。
**🗣️ 参考回答：**

我们主要处理长任务中的两类问题：一是代码、日志不断累积，超过模型的上下文容量；二是压缩历史时漏掉任务进度，导致 Agent 重复操作。参考 DSH 的做法，方案分成四部分。

**第一，按 Token 预算压缩历史，保留近期交互。**

每次请求模型前，检查上下文的 Token 占用。**低于模型窗口的 80% 时正常执行；达到 80% 时，先裁剪长工具结果，裁剪后仍达到 80%，再把较早的历史压成摘要。** 摘要时，从最新消息往前保留约占窗口容量 **16%** 的近期交互，其余较早历史生成摘要；保留边界会适当调整，避免拆开工具调用和对应结果。

**第二，工具输出分档裁剪，按完整调用组回收历史。**

短结果直接保留，较长结果保留关键片段，超大日志保存成文件，只给模型预览和文件引用。压缩旧历史时，工具调用和对应结果一起处理，不能拆开。**之后发给模型的是这段历史的摘要，而不是完整消息；完整消息仍保存在会话记录里，需要细节时可以查回原文。**

**第三，压缩前保存任务进度，压缩后补回关键信息。**

我们会单独记录任务要求、当前做到哪一步、改了哪个版本，以及哪些测试已经通过。例如，压缩前正在“等待回归测试结果”，压缩后就把这个进度明确告诉 Agent，让它接着查询测试，而不是重新分析 Bug。正在运行的构建或测试还会记录作业 ID，恢复时根据 ID 查询实际结果。

**第四，溢出后尝试压缩再重试，连续失败就停止。**

如果模型报上下文超限，我们先裁剪长工具结果，不够再把更早的历史压成摘要。输入缩短到预算内后，让模型继续执行原来的任务，最多重试一次；如果仍然超限，就保存任务进度并停止自动执行，避免反复发送同一份超长输入。
