###### 一面

**一、个人背景与教育经历**

1. **主问题：** 请先做一下自我介绍，后面我们再根据你的介绍，挑几个你认为做得比较好的项目展开讨论。（01:03）

2. **主问题：** 你简历上本科写了两所大学，是本科同时就读两个大学吗？（04:28）

**追问1：** 是跨学校的双学位吗？

**追问2：** 类似联合培养，还是其他形式？（04:56）

**二、项目选择与技术难度**

1. **主问题：** 你的大型项目经历比较丰富，但我们现在想招的是算法专家。你已经做过的项目里，最想讲哪两个？（05:27—06:22）

**追问1：** 不一定非要是上线项目，能不能挑你经历比较多、学习比较多、解决问题比较多的项目？

**追问2：** 解决这些问题时，你用了哪些技术、采用了哪些方案？

**追问3：** 上线或者用户需求本身，不代表实现一定复杂。能不能拿技术背景比较深、你认为做得比较好的项目来讨论？（06:51）

**三、Coding Agent 的业务痛点与自建必要性**

1. **主问题：** 你们做这件事的背景，是现有工具不能解决你们代码研发中的需求吗？（09:16—09:58）

**追问1：** 比如项目特别大，需要额外做索引，而现有工具不支持这方面的需求，是这个意思吗？

**追问2：** 我理解主要是两个问题：一是模型输入侧的代码理解不够，二是输出结果或交互不符合你们需求，需要二次开发，是这样吗？（11:25—11:56）

**四、平台边界与企业研发流程集成**

1. **主问题：** Deep Studio、企业级研发 Agent 平台，以及面向 Windows 的 Bug 自动修复平台，三者是什么关系？（12:52—13:48）

**追问1：** 是你做了一个代码平台，再接入其他 Agent 的能力，还是直接做了一个 Agent 平台，把相关代码研发能力放进去？

**追问2：** 我理解你们是把相关能力集中到一个平台里，而不是由其他平台接入你们提供的服务，是这个意思吗？（16:45—17:14）

**追问3：** 这会不会更接近一个工具，而不是平台？是不是提供了一套 Bug 修复环境，在上面串起修复和 CI 的流程？（17:14—18:42）

2. **主问题：** 为什么不把公司的 Agent 服务接入现有 CI 或代码托管平台，而是单独做一个 Bug 自动修复平台？（20:56—22:21）

**追问1：** Bug 修复只是软件工程中的一个环节，为什么要为这一个环节专门创建一个平台？

**追问2：** 需求、Spec、开发、测试、上线部署串起来才是完整流程。你们为什么选择当前这种组织方式？

**追问3：** 把自动修复能力作为服务或工具，接到已有平台的缺陷单入口，由后台完成拉代码、修复、构建和测试，不也可以吗？（26:11—29:00）

**追问4：** 你们有完整的产品经理来做这方面设计，还是研发接到需求后自己设计？（29:28）

**五、Agent Harness 架构与运行机制**

1. **主问题：** 你们的 Agent Harness 是自己搭的框架，还是复用公司内部已有的能力？（30:37）

2. **主问题：** 你刚才提到对话、任务和评审三种模式，这三种模式分别怎么实现？（32:02—33:01）

**追问1：** 如果要做自己的 Agent 框架，这几种模式在具体机制上有什么不一样？

3. **主问题：** 如果内核使用 Pi Agent，那么你们在内核外面具体封装了哪些东西？（33:31—34:29）

**追问1：** 也就是说，核心 Agent loop 是由所复用的内核提供的，对吗？

**六、小模型训练的目标与使用方式**

1. **主问题：** 简历中写到小模型训练和固定 Schema 输出，这项工作是为了解决什么问题？你怎么训练，又怎么把它用起来？（34:29—34:59）

**七、模型评估与正确性验证**

1. **主问题：** 你简历中小模型的通过数、总数这类结果，具体应该怎么解读？（36:55—37:24）

**追问1：** 我理解是根据工具调用的实际结果来做分析，对吗？（38:19）

**追问2：** 你提到的“理解能力”，具体怎么测？（38:49）

**追问3：** 你说模型能提取出正确的信息，那这个正确性是怎么保证的？（39:19—39:49）

**追问4：** 会采用类似 EM 的精确匹配，还是其他比较方式？（39:49—40:02）

**八、大型代码仓库的理解与检索**

1. **主问题：** 代码仓库理解是比较难的部分。你们的代码仓库理解怎么做？为什么要形成一个插件，这个插件有什么用？（40:02—40:31）

**追问1：** 我不是只问插件怎么实现，而是问代码仓库理解具体怎么做。（41:01）

**追问2：** 你说不让 Agent 使用默认的 grep 检索，那让它用什么方式检索？（41:32）

**追问3：** 你这个插件到底怎么找到代码？（42:27）

**九、RAG 的业务难点、方案价值与边界**

1. **主问题：** 第二个项目，是简历里的 Windows 研发与发布助手，对吧？（43:53—44:22）

2. **主问题：** 直接说核心难点：这个业务有哪些难点，RAG 解决了哪些问题？（46:19—46:48）

**追问1：** 使用 RAG 的过程中，有哪些问题仍然解决不了？

**追问2：** 你在这个过程中做了哪些创新工作？

**追问3：** 你为什么说原来的方式成本和延迟比 RAG 更高？（47:17）

**追问4：** 你所比较的传统检索方式具体怎么做，为什么会带来更高成本？（47:47）

**十、其他项目确认与反问入口**

1. **主问题：** 你简历里还有一个智能预约助手项目，是吧？（49:57）

2. **主问题：** 我这边大概了解了，你有什么问题想问吗？（50:27）
