# 方向二 · Agent 工具、协议与执行

> 覆盖：Agent 工具调用、结构化输出与 Function Calling 工程化、输出格式契约与 Schema 演进、工具设计工程（Tool Design）、MCP（Model Context Protocol）、A2A、代码执行沙箱与运行时隔离。

---

## Q1. 什么是 Function Calling / Tool Calling？它解决什么问题？
**答题要点**
- 模型不直接「调用」工具，而是**输出一个结构化的调用意图**（函数名 + 参数 JSON），由宿主程序去真正执行，再把结果回传给模型。模型负责"决策"，程序负责"执行"。
- 解决：让 LLM 能与外部世界（DB、API、计算、检索）交互，且交互格式**可解析、可校验**。
- 三种风格：OpenAI 风格原生 `tools` 字段、prompt 约定 + JSON 解析、受限解码（约束采样）。
**加分点**
- 讲清「**工具描述即 Prompt**」：name/description/参数说明直接决定选得准不准。
- 提「并行工具调用」：一轮里可返回多个调用，程序可并行执行（但要处理依赖与冲突）。

## Q2. 结构化输出怎么做？约束解码和 prompt 约束有什么区别？
**答题要点**
- 目标：让模型输出**可直接被程序消费**的合法结构（JSON/Pydantic）。
- **Prompt 约束**：在提示里要求格式 + few-shot，灵活但**不保证合法**，需解析失败重试。
- **约束解码**（JSON mode / 语法引导 / GBNF / Outlines）：解码时按语法掩码限制 token，**保证合法**，但对复杂 schema 有兼容限制、可能牺牲自由度。
- 工程落法：Pydantic/JSON Schema 定义 → 运行时校验 → 失败进入 **repair loop**（把错误回喂让模型修）。
**加分点**
- 把「解析失败率」当线上指标监控；对高风险场景做**双层校验**（模型约束 + 后端 schema 校验）。
- 用少量 few-shot 修高频错误，比反复加大约束更省。

## Q3. Schema 会演进，怎么设计才不把老客户端打挂？
**答题要点**
- 兼容原则：**新增可选字段优先**；枚举**只增不删**；避免改字段语义；用版本号字段标注 schema 版本。
- 渐进废弃：老字段先标记 deprecated、双写过渡、观察无调用后再移除。
- 消费端：解析时容忍未知字段（不要 strict 拒绝），对缺失字段给默认值。
**加分点**
- 提「契约测试」：一旦 schema 变更，跑一组固定样本回归，防止下游静默出错。
- 提「输出即 API」的心智模型——LLM 输出稳定性要像对外 API 一样管理。

## Q4. 工具怎么设计（Tool Design）？核心原则是什么？
**答题要点**
- 四原则：
  1. **粒度**：按「一个完整业务动作」切。太细 → 模型编排崩溃；太粗 → 失去灵活性。经验上 5~20 个工具较舒适。
  2. **幂等性**：写操作要能安全重试，带 `request_id` 去重，避免重试导致重复下单/重复发送。
  3. **描述工程**：name/description 写清「何时用、何时不用」，给正反例；描述就是给模型看的 API 文档。
  4. **错误契约**：失败返回**结构化、模型可理解**的错误（如 `{"error":"rate_limited","retry_after":5}`），而不是抛异常/堆栈，让 Agent 能自我纠正。
**加分点**
- 工具多了模型会"选不准" → **工具分组 + 二级路由 / 动态工具集**（按场景只暴露相关工具）。
- **返回值也要设计**：太长会污染上下文，要裁剪/摘要/分页。
- 高风险工具加 **HITL 人工确认 + 权限校验**，不靠模型自觉。
- 用「工具选择准确率」评估描述质量，工具描述要版本化 + 回归测试。

## Q5. MCP（Model Context Protocol）是什么？解决什么问题？
**答题要点**
- 一个**开放协议**，统一「LLM 应用 ↔ 外部工具/数据源」的接入方式，把 M×N 的定制集成变成 M+N 的标准接口。
- 核心概念：**Host**（如 Claude Desktop 这类宿主）、**Client**（连接器）、**Server**（暴露能力的一方）。
- 三类能力：**Tools**（可调用动作）、**Resources**（可读取数据）、**Prompts**（可复用模板）。
- 传输：stdio（本地）与 SSE/HTTP（远程）。
**加分点**
- 对比传统 Function Calling：MCP 把工具接入**标准化、可插拔、跨应用复用**，不再每个应用写一遍适配。
- 安全是重点：server 是第三方代码 → 需要权限最小化、能力声明、审批、沙箱；防止「工具投毒」（server 偷偷改描述诱导模型）。
- 可提生态趋势：MCP 之外还有 A2A（Agent 间协作）等协议在补位。

## Q6. A2A（Agent-to-Agent）和 MCP 有什么关系？
**答题要点**
- 定位不同：**MCP 面向「Agent ↔ 工具/数据」**，**A2A 面向「Agent ↔ Agent」**——让不同厂商、不同框架的 Agent 能互相发现能力、委派任务、交换结果。
- 典型要素：Agent Card（能力名片/发现）、任务（Task）生命周期、消息与产物（Artifacts）传递。
- 二者互补：一个 Agent 既可通过 MCP 用工具，也可通过 A2A 把子任务派给别的 Agent。
**加分点**
- 提互操作的价值：企业里"每个团队各建一个 Agent"时，A2A 让它们能编排成系统，而不用塞进一个巨型单体 Agent。
- 风险：跨信任域调用 → 身份、鉴权、审计、注入防护都要考虑。

## Q7. 代码执行沙箱怎么做？为什么"过滤危险函数"不够？
**答题要点**
- 场景：Code Interpreter 类 Agent 要执行**模型生成的代码** = 不可信输入，必须沙箱隔离。
- 隔离手段：容器/微虚机（gVisor、Firecracker、E2B 等）、**默认无网络或白名单出网**、文件系统只读 + 临时目录、CPU/内存/时间配额、超时强杀。
- 为什么过滤不够：字符串过滤/黑名单**绕过方式太多**（编码、反射、库调用），必须靠**隔离层兜底**（纵深防御）。
**加分点**
- **有状态会话**：同一多轮任务复用同一沙箱、状态可持久化，但要在任务结束彻底销毁。
- 产物回传：stdout/stderr/文件如何回给模型，注意**输出侧审查**。
- 防「沙箱成为外泄通道」：出网白名单 + 产物扫描 + 密钥不进沙箱。
- 资源计量既是成本控制也是安全边界。

## Q8. 并行工具调用（Parallel Tool Calling）怎么做？依赖怎么编排？
**答题要点**
- 背景：一轮里模型可能返回**多个 tool_call**。能并行的要**同时发起**（如一次查天气 + 一次查航班），不能并行的必须**串行**（后一步的入参依赖前一步的结果）。
- 判断依据：看**数据依赖**——有依赖 → 串行（B 的入参来自 A 的返回）；无依赖 → 并行。依赖关系可显式声明（DAG），也可由模型从上下文推断。
- 执行侧：并行要**并发派发 + 统一收敛**（asyncio.gather / 线程池），并各自带超时、重试、幂等；结果按 tool_call_id 回填到对应消息。
**加分点**
- 提「**并行不是免费的**」：会放大下游压力、争抢配额，需要**并发上限 + 背压**，否则把被调服务打挂。
- 提「**写操作要谨慎并行**」：多个有副作用的调用并行可能产生竞态/重复扣款，写操作更适合串行或加幂等键。
- 提部分失败处理：一轮里 3 个调用挂了 1 个，是**整体重试**还是**只重试失败项**（配合幂等 → 只重试失败项更优）。
- 与「ReAct 循环」的关系：并行工具用在**同一步**内，减少往返轮数 → 直接降延迟、降成本。
## Q9. 工具太多时怎么让模型选对？什么是工具检索与动态工具选择（Tool RAG）？
**答题要点**
- 问题：工具从十几个涨到上百个后（内部系统 + MCP server 聚合），把**全量工具塞进 prompt** 会：① 撑爆上下文、② 抬高成本与延迟、③ **选择准确率反而下降**（相似工具互相干扰、注意力被稀释）。
- 解法（**Tool RAG**）：把每个工具的 `name + description + 参数 schema` 当作"文档"，建向量索引；用户 query 来了先**检索 top-k 相关工具**，只把这 k 个注入模型上下文。
- 关键工程点：**工具描述质量决定检索质量**（描述要写清"什么时候该用我 / 不该用我"）；命名要语义化；可选加**命名空间/分组**（按系统或领域先粗筛再精挑）。
- 与静态选择的分界：工具数 ≤ 十几个、调用高度稳定 → 全量注入更简单可靠；数量大或按领域长尾分布 → 上检索动态裁剪。
**加分点**
- 提「**动态工具裁剪带来的风险**」：检索漏掉正确工具 → 模型直接答不上或乱编，所以要留**兜底**（无匹配时回退全量 / 允许模型主动"请求更多工具"）。
- 提「**工具描述就是 prompt**」：把 description 当产品文案迭代，用离线评测（给定 query → 期望工具）持续优化，这和 Prompt 优化同源。
- 提「**工具检索与工具设计是一体两面**」：粒度粗、职责重叠的工具既难检索也难调用；反过来，把上百个细粒度工具合并成少量"一个完整业务动作"的工具，本身就大幅降低了检索难度。
- 提「**MCP 时代的必要性**」：一个客户端同时挂多个 MCP server，工具总数轻松破百，工具检索成了必备的基础设施而非可选项。

## Q10. 工具调用出错时怎么让 Agent 自己绕过去？（错误回灌与自纠错 Error Feedback / Self-Correction）
**答题要点**
- 问题：工具必然出错（参数校验失败、超时、404、权限不足、业务拒绝）。两种极端都不好：① 把原始异常堆栈直接抛给模型 → 噪声大、模型容易被带偏甚至编造；② 默默 catch 掉返回空 → 模型以为成功，接着编造结果（假成功）。
- 正解：把错误**结构化、可行动地回灌（feed back）**给模型，让模型自己决定重试 / 改参数 / 换工具 / 放弃。
- 错误要分类：**可重试**（超时/限流/网络抖动）→ 退避重试；**可修正**（参数错误/字段缺失/类型不符）→ 把校验信息回传让模型改；**不可恢复**（权限不足/资源不存在/业务规则拒绝）→ 明确告知并禁止无意义重试。
- 回灌内容要素：错误类型 + 人类可读原因 + 修复提示（例如「参数 city 必填，有效值为枚举 …」）+ 是否可重试。
- 循环要有上限：最大重试次数、同一错误重复出现即终止（配合 Loop Detection / Termination）。
- 与幂等配合：重试只针对幂等调用或已带幂等键的调用；写操作重试前先查状态，避免重复扣款。
**加分点**
- 提「**错误消息是给模型最好的上下文**」：好的报错本身就是 few-shot，能显著提升自纠错率，把工具报错文案当产品来打磨。
- 提「**区分模型错 / 工具错 / 环境错**」：模型参数错 → 回灌修复；工具自身 bug → 直接告警，别指望模型修；环境抖动 → 框架层重试而非占用模型轮次。
- 提「**错误信号要进评测**」：统计工具失败率、**自纠错成功率**（首次失败后最终成功的比例），作为可靠性指标。
- 提「**避免假成功**」：HTTP 200 但业务失败（`success:false`）要靠结构化返回 + 后置校验（post-condition check）发现，不能只看状态码。
