# 方向一 · Agent 核心架构与推理循环

> 覆盖：Agent vs Chain、LangChain 抽象层次、Agent Executor、ReAct vs Plan-and-Execute、工具调用 ReAct 循环与 Self-Consistency、Reflexion、Agentic Workflow 与不确定性管理、长任务规划（Plan/Reflect/Replan）、Planner-Executor 解耦、状态机编排、LangGraph 持久化与 HITL。

---

## Q1. Agent 和 Chain 有什么区别？为什么需要 Agent？
**答题要点**
- **Chain**：执行路径在写代码时就固定了，`prompt → llm → parser → llm`，适合流程确定的任务（分类、抽取、固定 RAG 管道）。
- **Agent**：把「下一步做什么」的决策交给 LLM，模型根据当前状态动态选择工具、决定循环次数，适合路径不确定、需要多步推理+外部动作的任务。
- 本质差异：**控制流由谁决定**——Chain 由开发者写死，Agent 由模型运行时决定。
**加分点**
- Agent 代价：不确定性、成本不可预测、调试难。所以工程上常做「**受控 Agent**」——用 workflow 框住 Agent（该固定的步骤固定，只在需要决策的地方放开）。
- 面试官常追问「你这个其实就是 workflow，凭什么叫 Agent」——用「是否存在模型自主决策的分支」来区分。

## Q2. LangChain 的抽象层次是怎样的？
**答题要点**
- 自下而上大致是：**Models（LLM/ChatModel/Embedding）→ Prompts → Output Parsers → Chains（LCEL）→ Memory → Retriever/VectorStore → Tools → Agents → AgentExecutor**。
- 上层复用下层：Agent 复用了工具、模型、提示；Retriever 复用了 Embedding + VectorStore。
- 理解层次的价值：排查问题时能定位到具体层（是解析层出错还是检索层出错）。
**加分点**
- 能说清 LCEL（`|` 管道）如何统一同步/异步/流式/批处理接口。
- 版本演进：`AgentExecutor` → LangGraph 的图式编排，说明从「黑盒循环」走向「可控图」。

## Q3. Agent Executor 的工作流是怎样的？
**答题要点**
- 典型循环：**输入 → 组装 prompt（含工具描述+历史+scratchpad）→ LLM 输出 → 解析（是工具调用还是最终答案）→ 若工具调用则执行并把结果写回 scratchpad → 再次决策 → 直到给出最终答案或达到 max_iterations**。
- 关键部件：工具集合、prompt 模板、输出解析器、stop 条件（迭代上限、超时、终止 token）。
**加分点**
- 提「**scratchpad 会越滚越长**」，长任务必须做压缩/摘要或改成状态外置，否则上下文爆炸。
- 提可观测性：每步记录 tool 名、入参、出参、耗时，是线上排障的基础。

## Q4. ReAct 和 Plan-and-Execute 的区别？各自适用场景？
**答题要点**
- **ReAct**：Thought → Action → Observation 交替，**边走边想**。灵活、能根据观察修正，但步数多、成本高、易陷入循环。
- **Plan-and-Execute**：先让模型出**完整计划**，再逐步执行（可配 Replan）。前期规划开销大、计划可能过时，但结构清晰、可控、便于并行与缓存。
- 选型：短任务/需要即时反馈 → ReAct；长任务/步骤明确 → Plan-and-Execute；**混合**：先粗规划，执行中 ReAct 微调并 Replan。
**加分点**
- 提 Reflexion：执行失败后自我反思、把教训写回记忆再重试。
- 提「计划何时重规划」的判据（执行偏离、新信息出现、步骤连续失败）。

## Q5. Self-Consistency 在 Agent 工具调用里怎么用？
**答题要点**
- 让模型对**同一决策多次采样**（不同 temperature / 多次调用），取多数一致的结果，降低单次幻觉导致选错工具的概率。
- 适用于：关键分支决策（选哪个工具、是否终止）、高风险动作前的确认。
- 代价：token 与延迟成倍增长，只对「错一次代价很大」的节点用。
**加分点**
- 与「多次独立作答再对比」结合可检测**共识假象**（同源模型给同样的错答案）。
- 更省的替代：用便宜模型做 verifier 校验关键决策。

## Q6. Agentic Workflow 如何管理不确定性？
**答题要点**
- 不确定性的来源：模型输出随机、工具结果不可控、外部世界会变。
- 应对：① **结构化输出 + 校验重试** 降低格式不确定；② **置信度门控**（低置信度就澄清或升级人工）；③ **兜底与降级**（工具失败走备用路径）；④ **幂等 + 断点续跑** 抗中断；⑤ **预算上限**（步数/时间/token）防跑飞。
**加分点**
- 提「**Human-in-the-loop**」作为高不确定环节的最终兜底。
- 把不确定性做成可观测的指标（澄清率、重试率、降级率）。

## Q7. Agent 长任务如何做规划与任务分解（Plan / Reflect / Replan）？
**答题要点**
- **Plan**：任务拆成有依赖的子任务，形成 DAG / 待办清单。
- **Reflect**：执行中评估进展（是否偏离、是否完成），把结论写回状态。
- **Replan**：发现计划失效时重排剩余步骤，而不是从头再来。
- 工程要点：任务粒度适中；状态可序列化（存引用/结论而非大对象）；每步可验证。
**加分点**
- 提「计划即数据」——把计划存成结构化列表，便于暂停、恢复、人工干预、局部重试。
- 结合 LangGraph 的 checkpoint 做长任务续跑。

## Q8. 为什么要做 Planner 与 Executor 解耦？
**答题要点**
- 解耦后：规划用强模型（一次规划可复用），执行用快模型/专用工具，**成本与延迟更优**；职责清晰，便于分别评测与替换。
- 好处还在于可缓存计划、可并行执行子任务、可对执行层单独加权限控制。
**加分点**
- 风险：规划与执行的信息不同步 → 需要 Replan 机制与共享状态。
- 与「单体 ReAct」对比：简单任务别过度解耦，否则引入额外协调成本。

## Q9. 为什么用状态机/图来编排 Agent 工作流？
**答题要点**
- 纯 while 循环：可控性差、成本不可预测、失败难定位。
- **状态机/图**把控制流显式化：节点=步骤（检索/判断/调工具/生成/人工确认），边=转移条件，状态存 checkpoint。代表实现 **LangGraph 的 StateGraph**。
- 好处：流程可控、可回放、可恢复、异常可从中断点续跑。
**加分点**
- 状态设计要**小而可序列化**，大对象只存引用/ID，避免 checkpoint 膨胀。
- Graph 比 State Machine 更通用，状态机是受限但更清晰的形态。
- 条件边 + 循环边 = 既能分支又能重试。

## Q10. LangGraph 的持久化与 Human-in-the-loop 怎么实现？
**答题要点**
- **Checkpointer**（内存/SQLite/Postgres）把每一步状态落盘，形成 thread 的 checkpoint 序列。
- 作用：① **断点续跑**（进程挂了从最后 checkpoint 恢复）；② **时间旅行**（回到任意历史 checkpoint 重放/改分支）；③ **interrupt**（在指定节点暂停，等人工输入后继续）→ 这就是 HITL。
- HITL 典型场景：高风险工具调用前审批、关键决策人工确认、数据标注反馈。
**加分点**
- 提「状态与副作用要分离」：外部副作用（发邮件/下单）不能因重放而重复执行 → 用幂等键。
- 提 checkpoint 的存储选型与清理策略（长会话 checkpoint 无限增长）。
## Q11. GUI Agent / Computer Use 是什么？视觉驱动的操作怎么做？
**答题要点**
- **Computer Use / GUI Agent**：不调 API，直接像人一样「看屏幕 → 点鼠标 / 敲键盘」完成任务。动作空间是**屏幕坐标点击、输入文本、滚动、按键**这类低层原语，而不是结构化的函数参数。
- 运行循环：**截图（观测）→ 模型选动作 → 环境执行 → 再截图**，本质是一个 **POMDP 里的感知-动作闭环**。代表：Claude Computer Use、OpenAI Operator/CUA、browser-use，基准有 OSWorld / WebArena / WebVoyager。
- 工程要点：① **观测表示**——纯像素截图 vs 可访问性树（AXTree）/ DOM 结构化信息；② **坐标落点**——用 **set-of-marks** 给可交互元素编号引用，比裸坐标更准；③ **动作空间收窄**——只给受限原语，不给任意脚本执行；④ **历史压缩**——只留关键帧 + 动作摘要，用元素编号替代大段描述。
**加分点**
- 提「**混合观测**」：AXTree/DOM + 截图互补，比纯视觉更稳、更省 token。
- 提「**错误会累积**」：点错一步后面全乱 → 关键步骤前 re-observe 确认、动作去重防抖动、循环卡死检测、高风险动作（支付/删除）走 HITL 确认。
- 提「**与 RPA 的区别**」：RPA 靠固定选择器脚本，GUI Agent 靠模型泛化，脆性、成本、可审计性三者取舍不同。
- 提「**安全边界**」：它带着用户登录态跑，风险面等于浏览器本身 → 独立 profile/容器、域名白名单、敏感页面禁入。

## Q12. 树搜索式 Agent 推理是什么？（Tree Search / ToT / LATS）
**答题要点**
- **问题**：ReAct 是**单链贪心**——一步决定下一步、不回头。早期一个错误的选择往往不可逆，后面全歪。
- **思路**：把推理/动作展开成一棵**搜索树**，用**价值评估**给节点打分，再按 MCTS / beam 做「**选择 → 扩展 → 模拟 → 回传**」，允许**回溯**。
- 两个代表形态：**ToT（Tree-of-Thought）**只在**思考层**展开多分支并自评剪枝；**LATS（Language Agent Tree Search）**把 ReAct 与 MCTS 结合，**动作层也能回溯**（思考/行动/反思统一成节点），终局用环境反馈或自评打分。
- **本质**：用**额外算力换准确率**，属于 **test-time compute** 的一种用法。
**加分点**
- 提「**适用边界**」：适合**分支空间可控 + 有可验证信号**的任务（数学、代码、规划类 puzzle）；开放域长对话里分支爆炸、又没有可靠价值函数，搜索会**放大噪声**，性价比低。
- 提「**核心难点是价值评估**」：没有 verifier 时，节点打分本身就是弱信号，搜得越深越容易自信地跑偏。
- 提「**工程约束**」：分支因子/深度上限、剪枝、并行 rollout、节点缓存去重、token 与延迟预算。
- 提「**先便宜后昂贵**」：多数场景先用 ReAct + Reflexion 就够，树搜索是**明确需要精确解**时的升级选项。
