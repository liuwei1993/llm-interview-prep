# 方向七 · RAG 检索基础与优化

> 覆盖：RAG 三种检索策略、文档切分、Query Rewriting、混合检索与重排序（RRF / Cross-Encoder）、两阶段检索、向量索引与 ANN 性能优化（HNSW / IVF-PQ）、Embedding 模型选型、向量库选型与多租户、知识库增量索引与数据新鲜度。

---

## Q1. RAG 的三种检索策略是什么？
**答题要点**
- **稠密检索（Dense）**：用 Embedding 向量做语义相似度（ANN），擅长"意思相近但用词不同"。
- **稀疏检索（Sparse）**：BM25/TF-IDF 等传统倒排，擅长**精确关键词/专有名词/编号**。
- **混合检索（Hybrid）**：两者结合（常用 RRF 融合），互补——语义 + 精确。
**加分点**
- 提「**没有普适最优**」，要按语料特点选：代码/编号/术语多 → 稀疏权重高；口语/意译多 → 稠密权重高。
- 提「多路召回 → 融合 → 重排」是主流 pipeline。

## Q2. 文档该怎么切块（Chunking）？切块策略与原则？
**答题要点**
- 目标：块要**语义完整**且**大小适中**（太小丢上下文，太大噪声多、检索不准）。
- 策略：固定长度 + 重叠（overlap）、按语义/段落/标题切、按结构（表格/代码块单独处理）、父子块（小块检索、大块返回）。
- 原则：**按文档结构切**优于盲目按字符数；保留标题/路径等**元数据**做过滤。
**加分点**
- 提「**检索粒度 ≠ 生成粒度**」：小块利于检索命中，返回时补上相邻块/父块给模型。
- 提「**重叠窗口**」缓解切缝处信息断裂。
- 提「**按内容类型分别处理**」（表格、图表、代码不能用同一套切法）。

## Q3. 什么是 Query Rewriting？为什么要做？
**答题要点**
- 用户原始问题往往**口语、省略、指代不清**，直接检索命中率低。
- 改写手段：**查询扩展**（同义词/相关词）、**分解**（多跳问题拆成子问题）、**指代消解**（结合历史补全主语）、**HyDE**（先让模型生成假设答案再检索）、**多查询生成**（生成多个视角再融合）。
**加分点**
- 提「改写也要**防漂移**」：改完可能偏离原意，要用原查询兜底/融合。
- 提「**多查询融合用 RRF**」聚合结果。
- 提改写本身有成本与延迟，简单查询不必改写。

## Q4. 混合检索与重排序（Rerank）怎么做？为什么需要两阶段？
**答题要点**
- **两阶段**：① **召回（Retrieval）**——从海量语料快速捞 top-K（粗筛，追求快+高召回）；② **重排（Rerank）**——对候选精排（追求准）。
- **RRF（Reciprocal Rank Fusion）**：融合多路召回结果，用排名倒数加权，无需调权重、鲁棒。
- **Cross-Encoder Rerank**：把 (query, doc) 一起送模型算相关性，精度远高于向量相似度，但**慢**，只能对少量候选做。
**加分点**
- 提「**召回-重排的 K 值取舍**」：召回 K 大些保覆盖，重排 top-N 小些控延迟。
- 提「Rerank 能修正**向量相似 ≠ 相关性**的问题」。
- 提「延迟预算：重排加延迟 → 用轻量 reranker 或只对 top 候选重排」。

## Q5. 向量索引与 ANN 检索性能怎么优化？（HNSW / IVF-PQ）
**答题要点**
- 精确检索太慢 → 用 **ANN（近似最近邻）** 换取速度。
- **HNSW**：图索引，查询快、精度高、内存占用大；参数 `M`/`efSearch` 控制精度-速度权衡。
- **IVF-PQ**：倒排 + 乘积量化，省内存、适合超大规模，但精度有损；`nlist`/`nprobe` 调权衡。
- 优化手段：量化（PQ/SQ）、降维（Matryoshka）、筛选前置（元数据过滤后再向量检索）、分片。
**加分点**
- 提「**索引参数要在真实数据上调**」（召回率 vs QPS vs 内存）。
- 提「**过滤 + 向量检索**的顺序」：先过滤缩小范围往往比纯向量更快更准。
- 提「**更新频繁时索引重建成本**」影响选型。

## Q6. Embedding 模型怎么选型？换模型要注意什么？
**答题要点**
- 选型看：**MTEB 榜单**（任务维度）、语言（中/英/多语）、维度与成本、是否支持指令前缀、是否可本地部署。
- **Matryoshka**：支持"截断降维"仍保持较好效果，省存储与计算。
- **指令式前缀**：部分模型检索/文档要用不同前缀，用错效果差。
**加分点**
- 提「**换 Embedding 必须重建全量索引**」（新旧向量不可混用），且要重跑评测。
- 提「**领域适配**」：通用模型在垂直领域（医学/法律）可能不如领域模型或微调过的。
- 提「**混合检索补精确串**」：Embedding 对编号/专名的短板用稀疏检索补。

## Q7. 向量库怎么选型？多租户怎么隔离？
**答题要点**
- 选型维度：规模、延迟/QPS、过滤能力（metadata filter）、一致性、运维成本、是否要混合检索、能否自托管。
- 代表：FAISS（库，非服务）、Milvus、Qdrant、Weaviate、pgvector（贴现有 PG）、Elasticsearch/OpenSearch（天然混合）。
- **多租户隔离**：三种——**物理隔离**（每租户独立库/集群，最安全最贵）、**逻辑隔离 + 强制过滤**（共享库，查询必带 tenant_id 过滤，要防漏过滤）、**分集合/分区**（折中）。
**加分点**
- 提「**过滤字段要建索引**」，否则 metadata filter 拖慢查询。
- 提「**pgvector**：已在用 Postgres 时省一套系统，但超大规模要评估性能」。
- 提「**隔离的合规意义**」：多租户串数据是严重事故。

## Q8. 知识库增量索引与数据新鲜度怎么治理？
**答题要点**
- 需求：文档会新增/修改/删除，索引不能全量重建（太贵太慢）。
- 手段：**增量更新**（只重嵌入变更文档）、**软删除**（标记失效 + 检索时过滤）、**版本化**（保留版本，支持回滚/时间点查询）、**重嵌入策略**（换模型/改切分才全量重建）。
- 冲突处理：同一内容的旧版本要失效（去重 + 以最新为准）。
**加分点**
- 提「**变更检测**」（哈希/etc 判断是否需重嵌入）。
- 提「**新鲜度 SLA**」：新文档多久可被检索到，要可监控。
- 提「**删除的用户数据必须真能删干净**」（合规），软删除只是逻辑层。
- 提「**索引与源库的一致性**」：异步同步要有对账机制。
## Q9. Parent-Document Retriever（小块检索、大块生成）怎么做？
**答题要点**
- 核心矛盾：**块切得越小，向量匹配越准**（噪声少）；但块太小又会**丢上下文**，生成时答案不完整。
- 解法（**Small-to-Big / 小块检索、大块生成**）：索引与检索都用**子块（child chunk）**，命中后把它的**父块（parent document）或相邻窗口**交给 LLM。
- 三种常见实现：① **Parent-Document Retriever**——子块带 parent_id，命中后按 id 取回父块；② **Sentence-Window Retrieval**——命中单句，返回前后 N 句窗口；③ **Auto-merging Retriever**——同一父块下命中足够多个叶子块就合并回父块。
- 索引结构：向量库只存**子块向量 + parent_id 指针**，大块放在 docstore/parent_store 里 → 检索便宜、生成上下文完整。
**加分点**
- 提「**解耦了匹配粒度和生成粒度**」：两个目标不再互相妥协，这是它相对固定切分的本质优势。
- 提「**父块要裁剪去重**」：多个子块命中同一父块必须去重，并按命中数当相关性信号排序；父块过大反而引入噪声、挤占上下文预算。
- 提「**窗口/父块大小是超参**」，要按文档类型调（对话日志 vs 技术手册）。
- 提现成组件名：LangChain 的 `ParentDocumentRetriever` / `AutoMergingRetriever`，LlamaIndex 的 `SentenceWindowNodeParser` 等。

## Q10. 什么是 HyDE（Hypothetical Document Embeddings）？查询侧还有哪些增强手段？
**答题要点**
- 动机：用户 query 往往**又短又口语**，而知识库是正式文档，两者**语义空间有 gap**（"查询-文档不对称"），直接嵌入检索召回差。
- HyDE 做法：先让 LLM **凭 query 生成一段"假设性的答案文档"**（不需要正确，只要**风格像目标文档**），再对这段假设文档做 embedding 去检索。用"假答案"替代"真问题"去匹配"真文档"，把不对称拉齐。
- 代价与取舍：多一次 LLM 生成（**增加延迟与成本**），且假设内容可能带偏；所以常配 **多份假设文档取平均/并集**、或做**混合检索**兜底。
- 查询侧增强的其它常见手段：**Query Rewriting/Expansion**（改写扩写）、**Multi-Query**（生成多个视角子查询并行检索再融合）、**Step-back Prompting**（先问更抽象的上位问题）、**Query Decomposition**（多跳拆成子问题）、以及**查询意图分类 + 路由**（决定走哪条检索链路）。
**加分点**
- 提「**HyDE 适合冷启动 / 短查询场景**」，对已经很长很具体的 query 收益有限，甚至可能引入噪声。
- 提「**与 Query Rewriting 的区别**」：改写是在**问题空间**做归一，HyDE 是**跳到答案空间**再对齐——一个改问法，一个造答案。
- 提「**可只用假设文档的一部分**」或**混合检索**：把 HyDE 向量与原始 query 向量做加权/RRF 融合，兼顾召回与精度，比单用 HyDE 更稳。
- 提「**查询侧增强的通用原则**」：先解决"问得对不对"，再解决"检索得准不准"，最后才是"重排得精不精"——查询理解是 RAG 提效性价比最高的一层。

## Q11. 企业知识库怎么做权限感知检索？（Permission-aware Retrieval / ACL Filtering）
**答题要点**
- 问题：RAG 接的常是企业内部知识（HR/财务/研发），不同人可见范围不同。检索层不隔离，A 就能问出 B 无权看的机密 → **越权泄露**，是 RAG 最严重的生产事故之一。
- 核心原则：**权限在检索前生效（pre-filter），不是生成后过滤**。只在答案生成后"脱敏"不行——模型已经看到原文了。
- 三种落地层级：① **物理隔离**（每租户独立索引/库）；② **逻辑隔离**（同一索引里每个 chunk 带 ACL 元数据：部门/角色/用户组，检索时带 filter）；③ 混合（大租户独立、小租户共享带 filter）。
- ACL 建模：chunk 级权限标签（继承源文档权限）+ 用户身份（从 SSO/OAuth 拿）+ 检索时过滤表达式（如 `dept in user.depts AND level <= user.level`）。
- 向量库支持：多数向量库支持 metadata filter（Qdrant payload filter、Milvus expr、pgvector `WHERE`），要把 filter 和向量检索**一起做**（避免先取 top-k 再过滤 → 召回不足）。
- 特殊坑：**存在性泄露**——即使不给内容，命中数/高亮也会泄漏"存在某文档"；以及 **缓存/记忆跨用户复用**污染（语义缓存 key 必须带用户/租户维度）。
**加分点**
- 提「**权限变更的传播**」：文档权限改了、人离职了，索引里的 ACL 标签要跟着更新（与增量索引、TTL 结合），否则有窗口期越权。
- 提「**最小必要召回**」：在权限过滤后的**子集内**做 ANN（Qdrant 的 filterable HNSW、pgvector 的 iterative scan 等），避免"先 top-k 后过滤"导致结果为空/召回坍缩。
- 提「**审计与可追溯**」：每次检索记录"谁问了什么、过滤条件、命中哪些文档"，满足合规审计需求。
- 提「**权限是 RAG 与 Agent 安全的交汇点**」：Agent 能自主多次检索、还能调工具查数据库 → 权限必须同时下沉到**检索层和工具层**，不能只靠 prompt 里说"不要看机密"。


## Q12. 后期交互检索（ColBERT / Late Interaction）是什么？多向量检索怎么做？
**答题要点**
- 传统两段式：双塔（bi-encoder）做 ANN 召回，损失了细粒度交互；Cross-Encoder 精排效果好，但**每个 query-doc 对都要跑一次模型**，无法离线索引，规模上不去。
- **Late Interaction**（代表 ColBERT）：编码阶段完全独立（文档可离线编码），但相似度计算放到 **token 级**——query 的每个 token 向量与文档的每个 token 向量取最大相似度（MaxSim）再求和。既保留细粒度交互，又能靠倒排/ANN 索引做大规模检索。
- 代价：一篇文档要存**每个 token 一个向量** → 存储暴涨（常常几十倍）；工程上必须配合**向量压缩**：PQ 量化、维度裁剪（Matryoshka）、token 剪枝/聚类，把存储压回可接受范围（ColBERTv2 的残差压缩是经典做法）。
- 多向量检索的其它形态：文档切成多个 chunk 向量分别索引、多字段多向量（标题/正文分别编码）、以及把检索从"单向量"扩展为"多路向量 + 融合"。
**加分点**
- 提「**Late Interaction 是召回与精排的折中**」：介于 bi-encoder（快但粗）与 cross-encoder（准但慢）之间，本质是"**用存储换精度**"。
- 提「适合场景」：对**词级匹配敏感**的领域（专有名词、法律/医学条款、代码）收益明显；通用场景里 bi-encoder + rerank 性价比更高。
- 提「融合思路」：不必二选一——bi-encoder 先粗召回 → ColBERT/rerank 精排，或把 ColBERT 分数与 BM25/向量分数做 RRF 融合。
- 提「与混合检索的对比」：混合检索解决"稀疏 vs 稠密互补"，Late Interaction 解决"**交互粒度不足**"，两者正交、可叠加。
