# 方向三 · Agent 记忆与上下文工程

> 覆盖：Agent 记忆系统设计、记忆压缩与遗忘策略、Context Engineering、对话式 Agent 多轮状态管理与澄清提问、上下文组装/压缩。

---

## Q1. Agent 的记忆系统怎么设计？为什么要分短期和长期？
**答题要点**
- **短期记忆**：当前会话的工作记忆（对话历史、scratchpad、当前任务状态），随上下文窗口走，需要压缩。
- **长期记忆**：跨会话持久化的知识/偏好/经验，通常外置到向量库、KV 库或结构化存储，按需检索注入。
- 类比人脑：短期≈工作记忆，长期≈情节记忆（发生了什么）+ 语义记忆（事实）+ 程序记忆（怎么做）。
**加分点**
- 关键设计问题：**写什么、何时写、何时读、何时忘**——不是把所有东西都塞进去。
- 长期记忆要「**带元数据的结构化条目**」（时间、来源、置信度、类型），便于检索与冲突消解。
- 多租户/多用户时，记忆要有**隔离与权限**，别串号。

## Q2. 记忆压缩与遗忘策略怎么做？
**答题要点**
- 上下文有限，长会话必须压缩：**滚动摘要**（把旧对话摘成要点）、**层级摘要**（分段摘要 + 再摘要）、**关键信息抽取**（只留实体/决策/待办）。
- **遗忘**不只是删：可做**衰减加权**（旧且低频的降权）、**TTL 过期**、**冲突消解**（新事实覆盖旧事实）、**归档**（移到冷存储仍可召回）。
- 触发时机：接近窗口上限、话题切换、任务完成时固化。
**加分点**
- 提「**压缩是有损的**」——摘要可能丢关键细节，所以重要事实要**原文留存 + 摘要索引**双轨。
- 提「遗忘也是隐私保护」：GDPR/合规要求可删除用户记忆，需要可寻址删除。
- 用「记忆命中率 / 召回后是否有用」评估策略，而不是只看压缩比。

## Q3. 什么是 Context Engineering？它和 Prompt Engineering 的区别？
**答题要点**
- **Prompt Engineering**：优化**指令本身**怎么写。
- **Context Engineering**：优化**整个上下文窗口里装什么**——系统指令、工具定义、检索证据、记忆、对话历史、示例、临时状态，如何取舍、排序、压缩、组装。
- 它是「**在有限 token 预算下，让模型每一步拿到最相关的信息**」的工程。
**加分点**
- 经典发现：**Lost in the Middle** → 关键信息放头尾、中间易被忽略。
- 手段：检索注入、动态工具集、历史压缩、证据去重、结构化分区（用标记分隔）。
- 与「长上下文 vs RAG」联动：窗口大不代表该全塞，**信噪比**才是关键。

## Q4. 对话式 Agent 如何做多轮状态管理与澄清提问？
**答题要点**
- **Session State**：显式维护会话状态（已确认的槽位、当前目标、待办），别只靠对话历史"隐式记忆"。
- **Slot Filling**：把任务拆成必填槽位（时间、对象、范围），缺哪个问哪个。
- **指代消解**：把"它/那个/上次说的"解析成明确的实体（结合历史 + 实体表）。
- **澄清阈值**：置信度低于阈值或意图歧义时**主动提问**，而不是硬猜。
**加分点**
- 澄清要「**高效**」：一次问清多个缺失槽位，别来回挤牙膏。
- 提「澄清率 / 一次澄清成功率」当指标，澄清过多说明理解力不足。
- 状态要**可序列化 + 可恢复**，与 LangGraph checkpoint 打通。

## Q5. 上下文组装/压缩在真实框架里怎么做（以 Claude Code 为例）？
**答题要点**
- 组装：系统提示（规则/工具）→ 项目上下文（AGENTS.md 等）→ 会话历史 → 当前输入，按优先级与预算分配。
- 压缩：接近上限时**自动压缩**——摘要旧历史、保留最近若干轮原文、保留关键决策与工具结果。
- 文件/大块内容：**按引用而非全文**进上下文，用到时再读。
**加分点**
- 提「**分层加载**」：启动只加载必要文件，按需深度读，省 token。
- 提「**压缩要在正确的时机做**」（别在任务中途丢掉还没完成的步骤状态）。
- 记忆与压缩是**一体两面**：先决定什么值得长期留存，再决定什么只能在窗口内。

## Q6. 什么是 Lost in the Middle（长上下文中间遗忘）？怎么缓解？
**答题要点**
- 现象：模型对**上下文开头和结尾**的信息利用得好，**中间部分**容易被忽略——哪怕相关信息就在窗口里，也可能答不上来。这是**位置偏置**，不是「窗口不够长」。
- 原因：训练时位置分布 + 注意力衰减，导致中段「被稀释」；长上下文 ≠ 有效利用。
- 缓解：**关键信息放头/尾**（把最重要的证据、指令放最前或最后）；**精简上下文**（少而准 > 多而杂）；**检索按相关性排序**后把高分内容靠两端放。
**加分点**
- 提 RAG 实践：召回不是越多越好，**塞太多无关 chunk 反而拉低利用率**（噪声稀释），该排序、该剪枝。
- 提评测方法：用「针在草堆里」（Needle-in-a-Haystack）按**位置分桶**测，能看出中段衰减；再配合 RAGAS 等看真实问答质量。
- 提工程取舍：既然长上下文利用率会衰减，**「长上下文硬塞」往往不如「检索 + 重排 + 位置优化」**，别只堆窗口大小。
## Q7. Agent 的"经验记忆"与技能库怎么做？（Experience Memory / Skill Library）
**答题要点**
- 思路：让 Agent 把**成功/失败的解决过程沉淀下来**，下次遇到相似任务直接复用，而不是每次从零推理。典型形态是**技能库（skill library）**：每个技能是一段可复用的子流程/代码/工具序列，带触发条件与元数据。
- 代表工作：Voyager（Minecraft）把验证过的技能存进库、按需检索调用，实现持续自进化；反思式记忆（Reflexion）、Agent Workflow Memory（AWM）从历史轨迹里抽取"可复用工作流"。
- 关键闭环：**执行 → 反思/评估成败 → 抽取可复用经验 → 写入记忆 → 下次检索注入**；写入门槛要高（只存被验证有效的），否则会积累噪声与错误经验。
**加分点**
- 提「**经验要带元数据与置信度**」：成功率、适用场景、版本、来源，检索时按相关性 + 可信度排序，冲突时以新且高置信的为准。
- 提「**技能库会腐化**」：环境和 API 会变，老技能可能失效，需要**定期重验证 / 淘汰（TTL、失效回退）**，并保留"失败经验"避免重蹈覆辙。
- 提「**安全与可控**」：自动沉淀的技能等于**自我修改能力**，要有审查 / 沙箱 / 人工确认闸门，防止错误或恶意经验被固化传播。
- 提「**评估**」：看"复用后任务成功率、步数/成本下降、泛化到新任务的提升"，而不是只看存了多少条。
