# 方向六 · 多智能体系统

> 覆盖：多智能体协作架构、Supervisor/分层编排、系统级评测与协作失效模式、A2A 协议与 Agent 互操作。

---

## Q1. 什么是多智能体系统？常见架构有哪些？
**答题要点**
- 多个（不同角色/职责的）Agent 协作完成一个任务，而不是单个 Agent 扛全部。
- 常见架构：
  - **Supervisor / Orchestrator**：一个主 Agent 拆任务、分派给子 Agent、汇总结果（最常见、最可控）。
  - **Hierarchical（分层）**：多级 supervisor，适合大系统。
  - **Peer / 辩论（Debate）**：多个 Agent 平等讨论/互审，提质量但成本高。
  - **Pipeline（流水线）**：固定顺序，各 Agent 干一段（更像 workflow）。
  - **Blackboard / 共享状态**：Agent 通过共享黑板上读写协作。
**加分点**
- 关键：**"多智能体"不是越多越好**——很多任务单 Agent + 好工具更简单更便宜。多智能体的价值在**职责隔离、上下文隔离、并行**。
- 提「**上下文隔离**」：子 Agent 各自只装相关上下文，避免单 Agent 上下文爆炸。

## Q2. 多智能体系统怎么评测？协作会怎么"失效"？
**答题要点**
- 评测：除**结果质量**外，还要评**协作过程**——分工是否合理、是否重复劳动、是否互相甩锅、通信是否有效、总成本/延迟。
- 常见失效模式：
  - **信息丢失/误解**：Agent 间消息传递有损，认知不一致；
  - **责任稀释/死循环**：互相等待或互相推诿，任务打转；
  - **错误传播**：上游错误被下游当真值放大地传递；
  - **冲突与不一致**：多个 Agent 给出矛盾结论却无人裁决；
  - **成本失控**：Agent 互相调用导致调用次数爆炸。
**加分点**
- 提「**加裁决者/仲裁机制**」处理冲突。
- 提「**通信协议要结构化**」（别用自由文本传状态，用 schema）。
- 提「**上限与熔断**」防死循环（最大轮次/预算）。
- 提「多智能体 vs 单 Agent + workflow」的取舍：协作开销要换得来质量提升。

## Q3. 为什么 Supervisor 模式常常比"全连接辩论"更实用？
**答题要点**
- Supervisor 有**单一决策中心**：任务拆解、分派、汇总、终止判据都集中，可控性、可观测性、成本可控性都更好。
- 辩论式质量可能更高，但**成本成倍、收敛性差、难调试**，更适合离线/高价值场景。
- 实战折中：主流程用 Supervisor，**关键节点**（如高风险决策）引入少数 Agent 交叉验证。
**加分点**
- 提「**子 Agent 的接口要像工具**」（有明确输入输出契约），便于替换和测试。
- 提「**共享状态 vs 消息传递**」的取舍（共享状态一致但耦合，消息解耦但易丢信息）。

## Q4. A2A 协议（Agent-to-Agent）与 Agent 互操作是什么？
**答题要点**
- MCP 解决的是「Agent 怎么调工具 / 拿数据」（垂直方向），**A2A 解决的是「Agent 怎么和另一个 Agent 通信协作」**（水平方向），是一套开放的互操作标准。
- 关键抽象：
  - **Agent Card**：每个 Agent 对外声明自己是谁、有哪些能力、输入输出、认证方式，用于**能力发现**；
  - **Task**：有状态的任务对象，有 task id 与生命周期（提交 → 处理中 → 需要补充输入 → 完成/失败）；
  - **Message / Part**：多模态消息（文本、文件、结构化数据）；
  - **Artifact**：任务产出物。
- 传输：HTTP + JSON-RPC，支持**流式（SSE）返回**与**长任务推送通知**；中途可要求「用户补充信息」。
- 目标是让**不同厂商、不同框架**的 Agent 互相协作，不绑死单一生态。
**加分点**
- 提「**协议不是银弹**」：A2A 只解决连接与发现，多 Agent 协作真正的难点是**语义对齐、错误传播、成本失控**。
- 提「**Agent 间消息同样不可信**」——是间接 Prompt Injection 的载体，要做内容隔离与权限校验。
- 提认证授权（OAuth / 双向 TLS）与**最小特权**：跨组织 Agent 协作更要控制能做什么。
- 提「**不透明协作**」：只约定接口契约，不要求暴露对方内部 prompt 与工具实现。

## Q5. 子 Agent 上下文隔离与任务委派（Sub-agent / Context Isolation）怎么做？
**答题要点**
- 主 Agent 遇到大任务时，把子任务**派给子 Agent**；子 Agent 在**自己的独立上下文**里干活（读大量文件、检索、试错），只把**结论/产出**回传给主 Agent，中间过程**不进主上下文**。
- 核心价值：①**上下文隔离**——主上下文不被中间噪声和大量检索结果撑爆；②**职责单一**——子 Agent 只专注一件事；③**可并行**——多个独立子任务同时跑。
- 接口设计：子 Agent 的输入输出要有**明确契约（像工具一样）**——传参明确、返回结构化结果，便于替换与测试。
- 上下文传递策略：给子 Agent 的是「任务所需的**干净上下文**」，而不是主 Agent 的全部历史。
- 典型实现：Claude Code 的 subagent / Task 工具、Deep Agents 的子 Agent 委派、Supervisor 模式下的子节点。
**加分点**
- 提「子 Agent 的输出本质是一种**压缩（compression）**」：质量取决于摘要/提炼是否抓住要点，遗漏会导致主 Agent 决策错误。
- 提「子 Agent 也要有**预算与终止控制**」（步数/成本上限），否则派出去的子任务可能自己跑飞。
- 提「可观测性要能**下钻到子 Agent 轨迹**」，否则出错只能看到主 Agent 一层。
- 提取舍：只有任务「可独立、需大量上下文/试错、结果可压缩、可并行合并」时才划算；一步能干完的别绕。
