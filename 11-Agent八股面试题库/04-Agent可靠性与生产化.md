# 方向四 · Agent 可靠性与生产化

> 覆盖：工具执行的可靠性工程（超时/重试/幂等/熔断/降级）、失败恢复与断点续跑（Durable Execution / Checkpoint）、可观测性与线上评估、Agent 评测体系、成本-延迟-质量三角、并发与流式、灰度发布与 A/B、数据飞轮与反馈闭环、评测集与 CI 回归。

---

## Q1. Agent 的工具执行可靠性怎么保证？（超时/重试/幂等/熔断/降级）
**答题要点**
- **超时**：每个工具调用设合理超时，避免一个卡死拖垮整条链。
- **重试**：只对**幂等**操作自动重试；指数退避 + 抖动；重试次数上限。
- **幂等**：写操作带 `request_id` 去重键，服务端保证重复请求只生效一次。
- **熔断**：连续失败达阈值就"断路"，快速失败，避免雪崩；恢复期半开试探。
- **降级**：主路径失败走备用（换数据源、换模型、返回缓存或让模型用已有信息作答）。
**加分点**
- 区分「**可重试错误**（超时、限流）」与「**不可重试错误**（参数错、权限拒）」——别一律重试。
- 部分成功：一批操作里有的成功有的失败 → 要能报告并**只重试失败项**。
- 所有重试与降级都要**可观测**（重试率、熔断次数），否则线上问题看不见。

## Q2. 长任务失败怎么断点续跑（Durable Execution）？
**答题要点**
- 把任务切成**可持久化的步骤**，每步完成后把状态落盘（checkpoint）。进程崩溃/重启后从最后成功步骤恢复，而不是从头再来。
- 关键：**副作用与状态分离**——外部副作用（支付、发送、下单）绝不能因重放而重复执行，靠幂等键保证。
- 代表实现：LangGraph 的 checkpointer（内存/SQLite/Postgres）、Temporal 这类工作流引擎。
**加分点**
- 提「**确定性重放**」：恢复时用记录的输入重放，而不是重新决策，保证结果一致。
- 提 checkpoint 的**清理/归档策略**（长会话无限增长会拖慢）。
- 与 HITL 结合：人工审批点天然就是断点。

## Q3. Agent 可观测性怎么做？线上怎么评估质量？
**答题要点**
- **Tracing**：记录每一步（输入、模型、prompt、工具调用、观测结果、token、耗时），形成可回放的轨迹。工具：LangSmith、Langfuse、OpenTelemetry。
- **在线评估**：
  - **LLM-as-judge**：用模型按 rubric 打分（相关性、忠实度、完整性）；
  - **用户信号**：点赞/踩、追问、重试、复制、跳出；
  - **业务指标**：任务完成率、解决率、人工转接率。
- 关键：把指标与**具体轨迹**关联，出问题能定位到是哪一步、哪次工具、哪段检索。
**加分点**
- 提「**忠实度/幻觉检测**」单独监控（答案是否被证据支撑）。
- 提「**成本与延迟也要按步归因**」，找出最贵的环节。
- 提「**bad case 自动沉淀成评测集**」，形成发现→修复→防回归闭环。

## Q4. Agent 评测体系怎么搭？（组件评测 → 系统评测 → 发布闸门 → 上线监控）
**答题要点**
- **选型期（选基模）**：用统一评测集横评候选模型（任务成功率、成本、延迟）。
- **上线前 · 组件评测**：检索质量（命中率/NDCG）、工具选择准确率、解析成功率、单步质量。
- **上线前 · 集成/系统评测**：端到端任务成功率、多轮一致性、鲁棒性（脏输入/注入）、成本与延迟。
- **发布闸门（Pipeline）**：把评测做成 CI 里的硬门槛，不达标不许发。
- **上线后监控**：真实流量指标 + 异常告警 + 定期抽检。
**加分点**
- 提「**评测集要版本化、防污染**」（别拿训练/调 prompt 用过的样本当测试集）。
- 提「**用 LLM-as-judge + 人工抽检交叉验证**」，避免 judge 自身偏差。
- 提「Agent 评测 vs 传统评测」差异：路径不唯一、结果不完全可复现 → 更看重**结果正确性 + 过程合理性**。

## Q5. 成本-延迟-质量三角怎么权衡？
**答题要点**
- 三者通常互斥：更强模型 = 更好质量但更贵更慢；多轮反思/多路投票 = 更好质量但翻倍成本。
- 策略：**按任务分层**——简单问题走便宜快链路，复杂问题才升级到强模型/多步；**缓存**复用；**并发/流式**降感知延迟；设**预算上限**防跑飞。
- 目标不是"都最优"，而是**在 SLA 内达到可接受质量的最低成本**。
**加分点**
- 提「模型级联/路由」实现按难度分配算力。
- 提「延迟预算」：把总预算拆给各步，超预算就降级。
- 用「每解决一个任务的成本」当北极星指标，而不是单次调用价格。

## Q6. Agent 的并发与流式怎么做？
**答题要点**
- **并发**：一轮内多个独立工具调用可并行执行（降低总延迟）；多用户请求要隔离状态、限制并发、做背压/限流。
- **流式**：流式输出 token（降感知延迟）、流式工具事件（实时展示进度）。SSE/WebSocket 传输。
- 难点：流式 + 结构化输出（边解析边校验）、流式中断与重连、流式下的计费与截断。
**加分点**
- 提「**幂等 + 有序**」：并发写要保证顺序与一致性。
- 提「异步框架」的选择（asyncio/事件循环）与阻塞调用的坑。
- 提「首 token 延迟（TTFT）」是体验关键指标。

## Q7. LLM 应用怎么做灰度发布与 A/B 实验？
**答题要点**
- 三步走：**Shadow（影子流量）**新版本只跑不对外 → **Canary（金丝雀）**按比例放量（1%→5%→50%）→ **A/B 实验**按用户分组对比业务指标。
- 流量切分：按用户哈希（同一用户稳定落同组，避免体验抖动）或按会话。
- 上线必须配**一键回滚开关（feature flag）**。
**加分点**
- LLM 特有困难：输出非确定、评测贵、质量主观 → **LLM-as-judge + 人工抽样 + 业务指标**三线并行。
- 实验要**算样本量**，不能几十个请求就下结论。
- 提「离线评测通过 ≠ 线上变好」，灰度是最后一关。

## Q8. 什么是数据飞轮 / 反馈闭环？怎么落地？
**答题要点**
- 闭环：埋点收集真实 query 与结果 → 收集显式反馈（点赞/踩、修正）与隐式信号（追问、重试、复制、跳出）→ 筛高价值样本 → 补进评测集/用于微调或优化检索与 prompt → 再上线验证。
- 显式反馈稀疏但精确，适合**精标**；隐式信号多但有噪声，适合**粗筛 + 归因**。
**加分点**
- 提「**反馈 ≠ 真值**」：点赞的可能碰巧错 → 需专家抽检或 LLM-as-judge 交叉验证。
- 提**数据合规与隐私**（PII 脱敏、授权范围）。
- 提**节奏感**：初期人工种子数据，成熟后才逐步自动化。
- 提「线上 bad case → 回归评测集」是飞轮的核心价值。

## Q9. 评测集与 CI 回归测试怎么做（Eval-driven Development）？
**答题要点**
- 把「评测」当软件测试：每次改 prompt/模型/检索都跑固定评测集，指标不降才允许合并。
- 组成：单元（单步：检索/解析/工具选择）+ 集成（端到端任务）+ 回归（历史 bad case）。
- CI 门禁：设定阈值，低于阈值阻塞发布；记录每次指标变化趋势。
**加分点**
- 提「**评测集要有覆盖面 + 难度分层**」（易/中/难）。
- 提「**防止评测集过拟合**」：holdout 集只在最终决策用。
- 提「**人工标注规范 + 多标注者一致性**」保证标签质量。

## Q10. Agent 的工具调用能力怎么评？有哪些基准（benchmark）？
**答题要点**
- 评"工具调用"要拆成三层：**工具选择**（选不选、选哪个）、**参数构造**（schema 是否填对、类型/必填/多工具）、**多步编排**（多轮调用、依赖顺序、能否并行）。
- 常见公开基准：
  - **BFCL（Berkeley Function Calling Leaderboard）**：考单轮/多轮 function calling 的**选择与参数正确性**，用 AST / 可执行校验打分，是目前最常被引用的工具调用榜。
  - **τ-bench（tau-bench）**：**有状态多轮**场景（如航空/零售客服），带**数据库状态与业务规则**，用 **pass^k** 衡量「k 次里每次都成功」的**一致性/可靠性**——专门揭示"单轮分数高、多轮就崩"的问题。
  - **AgentBench / GAIA / SWE-bench**：端到端 agentic 任务；GAIA 考真实世界多步检索+推理，SWE-bench 考真实代码仓库改 bug。
- 指标：成功率（pass@1 / pass^k）、调用轮次、**无效调用率**、参数准确率、成本与延迟。
**加分点**
- 提「**pass^1 高 ≠ 可靠**」：生产更看 **pass^k**——用户要的是**每次都对**，τ-bench 正是为此设计。
- 提「**公开榜有污染、且与你的场景不匹配**」：榜单只能初筛，**必须自建场景评测集**（真实 query + 真实工具 + 业务规则）。
- 提「**评测要模拟脏输入**」：工具报错、返回超大结果、权限拒绝、并发冲突，这些才是线上最容易翻车的地方。
- 提「**成本/延迟也是评分项**」：多调几轮有时数据更好但不划算，要用"每任务成本"而非"单次调用价"衡量。

## Q11. Agent 为什么会死循环？终止条件（Loop Detection / Termination）怎么设计？
**答题要点**
- Agent 本质是「模型决策 → 工具执行 → 再决策」的**循环**，天然可能不收敛，必须显式设计终止条件。
- 常见失控模式：①**原地打转**——同一工具、同一参数反复调用；②**错误前提上反复重试**；③**无休止 Replan**（每次都推翻重来）；④**空转**——模型反复"我再确认一下"却不产出。
- **硬上限**：最大步数（max iterations）、最大 token、最大时长/费用预算，触顶强制终止（保底，但可能过早掐死正常长任务）。
- **软检测**：动作去重（把 `tool + 参数` 归一化后重复 N 次即中断）；状态哈希 / 无进展检测（连续 k 步状态或产出无变化即判定卡住）；语义相似度检测（近似动作算重复）。
- **显式终止信号**：要求模型输出 `final_answer` 或调用 `finish` 工具来结束，而不是靠"自然停下"。
- 中断后处理：**降级**（返回已有最优结果）或**升级**（转人工）。
**加分点**
- 提「为什么会死循环」：模型不确定 + 缺少明确终止判据 + 工具反馈无效（返回空/报错却不给纠正信息）。
- 提「硬上限 vs 软检测」的差别：硬上限保底但不智能，软检测精准但需设计判据，**两者要配合**。
- 提「怎么区分合理重试与死循环」：看这一步是否带来**新信息 / 状态推进**。
- 提「把 loop rate、平均步数、超限率当独立可观测指标」，并用状态机/图显式建模终止态。
